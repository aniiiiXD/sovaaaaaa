# API reference and workflow

Base control URL: `http://127.0.0.1:8787/api/v1`. Inference base: `http://127.0.0.1:8787/v1`.

Every resource request uses `Authorization: Bearer <RIG_API_TOKEN>`. IDs are 32-character lowercase hexadecimal strings generated by Rig. Every HTTP response includes `X-Rig-Request-Id`.

Error envelope: `{"error":{"code":"...","message":"...","request_id":"..."}}`. Validation failures return 422, missing resources 404, state/leakage conflicts 409, disabled/busy execution 503, and oversized bodies 413. Requests reject unknown fields. A default maximum 20 MB request body is enforced even without Content-Length.

## Customer workflow API

Use [WORKFLOW.md](WORKFLOW.md) and [workflow.http](../examples/workflow.http) for the
complete loop. These endpoints compose the low-level stage APIs. Submission only queues work.

| Method | Path under `/api/v1` | Result |
|---|---|---|
| POST | `/candidates/import-local` | 202 local model import job |
| POST / GET | `/workflows` | Create/list immutable workflow definitions |
| GET | `/workflows/{id}` | Task, owner, policy and pipeline template |
| POST / GET | `/workflows/{id}/cycles` | Queue/list cycles and jobs |
| GET | `/workflows/{id}/cycles/{cycle}` | Cycle configuration and job result |
| GET | `/workflows/{id}/cycles/{cycle}/failures` | Validation errors |
| POST | `/workflows/{id}/cycles/{cycle}/release` | 202 test-split audit |
| POST | `/workflows/{id}/cycles/{cycle}/promote` | Promote an accepted release |
| GET | `/workflows/{id}/feedback` | Workflow-scoped production feedback |
| POST | `/feedback/{id}/review` | Immutable approval/rejection |
| GET | `/feedback/{id}/reviews` | Review records |

Pipelines also accept `baseline_candidate_id` and `comparison` with `min_score_gain`,
`max_latency_ratio` and `max_estimated_cost_ratio`. Both candidates use the same
configuration and dataset. See WORKFLOW.md for measurement and cost limitations.

## 1. Dataset

```json
{
  "name": "task-v1",
  "description": "Reviewed task examples with fixed holdouts",
  "records": [
    {"prompt":"Training question", "completion":"Expected answer", "split":"train"},
    {"prompt":"Different validation question", "completion":"Expected answer", "split":"valid"},
    {"prompt":"Different final test question", "completion":"Expected answer", "split":"test"}
  ]
}
```

Records also accept an optional `system` string and optional unique `id`. `parent_id` links a dataset to a previous version. Training requires at least `batch_size` examples in both train and valid. This tiny example needs batch size 1 and is illustrative, not a useful training set. [The example file](../examples/dataset.json) includes a slightly larger synthetic import fixture.

## 2. Base candidate

```json
{
  "name": "qwen-base",
  "repo_id": "mlx-community/Qwen3-0.6B-bf16",
  "revision": "<actual 40-character commit SHA of the chosen model>"
}
```

Replace placeholders before submitting. A moving branch like `main` is rejected. Registration stores metadata only; execution resolves the pinned snapshot from cache unless downloads are enabled. Choose a compatible chat model that does not require remote Python code.

## 3. Complete pipeline

```json
{
  "training": {
    "base_candidate_id": "<candidate-id>",
    "dataset_id": "<dataset-id>",
    "name": "task-specialist-v1",
    "iterations": 600,
    "batch_size": 2,
    "learning_rate": 0.0001,
    "lora_rank": 8,
    "lora_scale": 20,
    "lora_dropout": 0,
    "num_layers": 16,
    "max_seq_length": 2048,
    "seed": 42
  },
  "evaluation": {
    "dataset_id": "<dataset-id>",
    "split": "valid",
    "metric": "normalized_exact",
    "generation": {"max_tokens": 64, "temperature": 0, "seed": 42},
    "gate": {"min_score": 0.85, "max_p95_latency_ms": 1500}
  },
  "optimization": {
    "strategy": "quantize",
    "bits": 4,
    "group_size": 64,
    "max_score_drop": 0.01,
    "max_latency_ratio": 1.0
  }
}
```

Use `optimization: null` to stop after training/evaluation. Thresholds above are examples, not measured recommendations. Choose them for the task. Set `estimated_hourly_usd` in the evaluation config only when an estimate has a meaningful basis. `gate.max_estimated_usd_per_1k` then optionally imposes a cost constraint.

The response is a queued job, never a claim that training has succeeded. The worker must be separately started and execution enabled. Poll the job; its result selects the passing tuned candidate when optimization fails its gates. No deployment is changed by this pipeline.

For stage-by-stage use, submit the `training` object to `/training`. Submit the `evaluation` object plus `candidate_id` to `/evaluations`. Submit `baseline_report_id` and optimization fields to `/optimizations`.

## 4. Iterate

Get `/evaluations/{report-id}/failures`, inspect the error pattern, and write **new** training examples. Submit:

```json
{
  "name": "task-v2",
  "pipeline": {"training":"<same training object>", "evaluation":"<same evaluation object>", "optimization":null},
  "new_training_records": [
    {"prompt":"A newly authored training case", "completion":"Reviewed answer", "split":"train"}
  ]
}
```

The nested strings above stand for objects from step 3; this is a shape illustration. Use the prior dataset ID in `pipeline.training.dataset_id`. Rig appends examples into a child dataset and updates pipeline references to that child. Retraining normally starts from the original base candidate. Fuse an adapter first if intentionally training from its weights. Failed submissions after dataset creation may leave a valid unqueued dataset version; it is visible in the dataset list.

## 5. Final test, promotion and rollback

Submit `/evaluations` with the selected `candidate_id`, the held-out dataset, and `split:"test"`. Inspect its report. Promote the passing report:

```json
{"name":"task-specialist", "report_id":"<passing-report-id>"}
```

Promotion accepts passing validation or test reports; use a final test report for a release when that is your policy. Gates are explicitly supplied experiment policy, not automatic proof of general model quality. To roll back, promote the previous passing report under the same name. The earlier history remains available.

## 6. Serving and feedback

```json
{
  "model":"task-specialist",
  "messages":[{"role":"user", "content":"A real task"}],
  "max_tokens":128,
  "temperature":0,
  "stream":false
}
```

The response follows the text chat completion shape with `choices`, `usage`, `model` and `id`. This is a subset: tools, images, streaming, logprobs, arbitrary provider parameters and the Responses API are not implemented. Unsupported fields are rejected rather than ignored. The model alias must exist and execution must be enabled.

Use the raw `X-Rig-Request-Id` header for feedback, not the `chatcmpl-` response ID:

```json
{"request_id":"<request-id>", "rating":"bad", "correction":"Human-reviewed correct answer"}
```

With content retention enabled at inference time, select feedback IDs and submit `/datasets/from-feedback` with `{"name":"corrections-v1","feedback_ids":["<feedback-id>"]}`. The result is train-only; merge its records into a version with held-out validation data before training. Multi-turn feedback import is explicitly rejected in this version. Existing held-out prompts still cannot become training examples.
